# tile 形状枚举分析（纯分析，未改代码）

指令排布线路关闭后（wave_pingpong −6.75%、vmem_interleave 判零、sched_probe
0 candidate），问题是：在现有约束下换 tile 形状能不能把 MFU 推到 60%。

结论：**不能。所有可行形状的模型性能完全相同（2.819 P / 56.3%），最优形状
相对当前 +0.0%。这条路不值得做。**

## 约束（全部从源码读出，非假设）

- `BLOCK_SIZE=512` = 8 waves，`NUM_WAVES == T_M*T_N*T_K`
- MFMA 16x16x128 → `W_M=W_N=16`, `W_K=128`, `B_K % 128 == 0`
- `HALF_B_M % (W_M*T_M) == 0`、`HALF_B_N % (W_N*T_N) == 0`（M/N 都对半分）
- LDS：A、B 各 `smem_?_rep*(1024+32) * 2 halves * 2 stages`，加 2 stage scale。
  上限 163840 B。**校准验证：256x256x128 → 139264 B，与编译器逐字节一致。**
- VGPR：accumulator = `4 quadrants * E_M*E_N * 4 dwords`，非 acc 开销按
  256x256x128 实测（236 总 / 128 acc）标定，上限 256。

33 个形状可行。

## 关键修正：减法阶梯的 global 项不是流量成本

初版模型把"减 global load = 0.0286 ms"当成流量成本按字节缩放，得出所有形状
几乎无差别。这个模型有内部矛盾：

```
A+B 全局流量 @256x256 = 4.4 GB
4.4 GB / 0.0286 ms = 153.8 TB/s      <- 不可能，实测 HBM read 6.119 TB/s
4.4 GB / 6.119 TB/s = 0.7191 ms      <- 比整个 kernel(0.4485ms)还长
```

所以 **0.0286 ms 是流水线掩盖之后剩下的"暴露等待"，不是搬运成本**。真正的
DRAM 时间被 L2 吸收了（实测命中率 72.8%，DRAM 侧 1.20 GB → 0.196 ms）。

形状改变的是**总流量**进而是 DRAM 底线，不只是那 0.0286 ms。改用
`max(计算底线, DRAM底线) + 暴露等待` 重算。

```

 256x256x128  4x 2  2x4  128  236 139264  1.000  0.1969   0.3900   2.819 56.3% compute  <- 当前
 384x192x128  4x 2  3x3  144  252 156672  1.000  0.1908   0.3900   2.819 56.3% compute
 256x192x128  4x 2  2x3   96  204 121856  1.167  0.2261   0.3900   2.819 56.3% compute

 ...
 128x128x128  4x 2  1x2   32  140  69632  2.000  0.3938   0.4224   2.603 52.0%    DRAM
```

**33 个形状里 32 个是 compute-bound，模型时间逐位相同。** 只有 128x128 小到
变成 DRAM-bound，而它是唯一一个更差的。

当前形状要变成 DRAM-bound，需要 L2 命中率跌到 **49.7%** 以下；实测是 72.8%。
DRAM 项有大量余量，**换形状是在优化一个不绑定的项**。

## 时间去向（实测，非模型）

| 项 | 时间 | 占比 |
|---|---:|---:|
| MFMA+LDS 骨架 | 0.3215 ms | **71.7%** |
| C store | 0.0399 ms | 8.9% |
| 暴露的 global 等待 | 0.0286 ms | 6.4% |
| 模型合计 | 0.3900 ms | — |
| 实测 | 0.4485 ms | — |

模型比实测少 0.0585 ms（13%），那是三项之外的开销（prologue/epilogue、tile
边界、traversal），本分析未建模。

## 天花板

```
若 global 路径完全免费：      0.3614 ms → 3.042 P (60.8% MFU)
若 C store 也完全免费：       0.3215 ms → 3.420 P (68.3% MFU)
```

**60% MFU 需要 global 等待归零。** 而 C store 已在物理写带宽极限
（134.2 MB / 0.0399 ms = 3364 GB/s，本机实测写带宽 5233 GB/s，同量级），
不可能再压。

## 结论

1. tile 形状**不是**杠杆——32/33 的形状 compute-bound 且模型时间相同。
2. 真正的大头是 **MFMA+LDS 骨架的 0.3215 ms，占 71.7%**。这是 16x16x128 MFMA
   指令数 × 每条延迟 + LDS 读带宽的乘积，不随 tile 形状变。
3. 要动这 71.7%，只有换 MFMA 形状（`gemm_a8w8_mxfp8_scale_common.h` 里已有
   一个 32x32x64 的实验 traits，MFMA 指令数减半），或减少 LDS 往返。
4. 本机 68.3% 是纯骨架上限；60% 目标要求 global 等待完全归零，而指令排布线路
   已证明榨不动。
