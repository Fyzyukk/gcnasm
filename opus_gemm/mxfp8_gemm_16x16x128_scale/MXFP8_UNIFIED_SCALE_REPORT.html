0. 内核骨架

先看整体形状，后面每一步都挂在这个骨架的某个位置上：

__global__ __launch_bounds__(512, 2)
void gemm_a8w8_mxfp8_scale_kernel(kargs) {

  // ── prologue：wave 角色、scale 描述符选择（跨 output tile 存活）
  scale_producer_active / scale_producer_is_sfa / g_sf / stride_sf / s_sf_ptr

  for (output_tile = 0; output_tile < 4; ++output_tile) {   // 持久 M tile 循环
      if (block_m >= num_tiles_m) break;

      // ── 布局构造（编译期）+ LDS 声明
      // ── prologue：output_tile==0 时预载 tile 0；loops>1 时种入 cold B

      #pragma unroll 4
      for (tile = 0; tile + 1 < loops; ++tile) {            // 主 K 循环
          ds_read  当前 tile 的 sfa / sfb / A0 / B0 / B1前半
          async_load 下一 tile 的 scale / A0 / A1
          32 条 MFMA（C[0][0] 和 C[1][0]）
          单 barrier：发布 t+1、回收 t 的 LDS
          发 t+2 的 cold B（仅 producer wave）
          32 条 MFMA（C[0][1] 和 C[1][1]），与上面的 B 搬运重叠
      }

      // ── 尾 tile：只消费，不再发 global；同时预取下一个 output tile
      // ── C 写回（nt）
  }
}

1. 优化逐条拆解

1 · 持久 fixed-B：一个 workgroup 连算 4 个 M tile 结构

问题。一个 workgroup 只算一个输出 tile 时，每算完一块，B 和 SFB 就要重新从 global 拉一遍。

做法。让一个 workgroup 沿 M 方向连续吃掉 4 个相邻 tile。整个过程 col（N 坐标）不变， 于是 B 和 SFB 一次都不用重载： 

template<class Traits>
struct fixed_b_prefetch_4_traits : Traits {
    static constexpr int OUTPUT_TILES_PER_WG = 4;   // 与主机网格规则耦合，不可独立调
};

const int block_n       = block_id_x() % num_tiles_n;
const int first_block_m = (block_id_x() / num_tiles_n) * T::OUTPUT_TILES_PER_WG;
const int col           = block_n * T::B_N;         // ← 循环外，全程不变

for (int output_tile = 0; output_tile < T::OUTPUT_TILES_PER_WG; ++output_tile) {
    const int block_m = first_block_m + output_tile;
    if (block_m >= num_tiles_m) break;              // M 不整除时的尾部保护
    const int row = block_m * T::B_M;               // ← 只有 A 侧随循环推进
    ...
}

主机侧网格必须配合，否则会漏算或重算：

grid.x = ceil_div(num_tiles_m, 4) * num_tiles_n;
grid.z = batch;
为什么是 4，不是 8 或 16 8 和 16 都实测过：VGPR/LDS 完全不变、数值全对，但更慢。 瓶颈不是 A 的重复流量，而是 CU 占用——workgroup 总数随之减少，填不满 CU。 所以 4 是实测最优点，不是一个可调参数。

2 · 双缓冲滚动流水线 结构

做法。LDS 里 A/B 各开 4 份、scale 各开 2 份，用 stage ^ 1 在两组之间翻转。 每轮循环一边从 stage 读当前 tile、一边往 stage^1 写下一 tile： 

__shared__ char smem_a[smem_a_elem * 4 * sizeof(D_A)];    // 2 stage × 2 half
__shared__ char smem_b[smem_b_elem * 4 * sizeof(D_B)];
__shared__ char smem_sfa[smem_sfa_elem * 2 * sizeof(D_SF)];
__shared__ char smem_sfb[smem_sfb_elem * 2 * sizeof(D_SF)];

auto sa_offset = [&](int stage, int half) { return (stage*2 + half) * smem_a_elem; };
auto sb_offset = [&](int stage, int half) { return (stage*2 + half) * smem_b_elem; };

for (tile = 0; tile + 1 < loops; ++tile) {
    const int next_stage = stage ^ 1;
    ... 读 stage，写 next_stage ...
    stage = next_stage;  scale_stage = next_stage;
}

关键在于 async_load 走的是 gfx950 的 buffer_load_dwordx4 … lds—— global 直接落 LDS，不经过 VGPR。所以「预取下一 tile」这件事不占累加器寄存器， 这是能在 240 VGPR 的预算里同时容纳双缓冲的前提。

3 · 16 字节 scale producer scale 通路

问题。scale 载荷只有 2 KiB/K tile（SFA 1 KiB + SFB 1 KiB）， 但早期的 4B 协同路径要 8 个 wave 各发一条 4B/lane 的 VMEM——8 条 wave 级请求搬 2 KiB。

做法。改成两个 wave 各用 16B/lane 一次搬完：

wave 0: 64 lanes × 16 B = 完整 1 KiB SFA tile
wave 1: 64 lanes × 16 B = 完整 1 KiB SFB tile

wave 级 scale VMEM 8 条 → 2 条，总载荷和 LDS 图像都不变。用显式 layout 表达：

// global 侧：lane 作为 tile 内的行坐标，stride = [16, 1]
constexpr auto block_shape = make_tuple(number<WARP_SIZE>{}, number<16>{});
return make_layout<16>(block_shape,
    unfold_x_stride(block_dim, block_shape, tuple{number<16>{}, 1_I}),
    unfold_p_coord(block_dim, tuple{lane_id}));          // ← 有 lane 坐标

// LDS 侧：不加 lane 坐标
constexpr auto block_shape = make_tuple(number<16>{});
return make_layout<16>(block_shape,
    unfold_x_stride(block_dim, block_shape, tuple{1_I}),
    unfold_p_coord(block_dim, tuple{}));                 // ← 空
为什么 LDS 侧不带 lane gfx950 的 buffer_load_dwordx4 … lds 从一个 wave-uniform 的 LDS base 开始， 硬件会把各 lane 的 16 字节返回值依次写进去。lane 偏移由硬件负责， 软件再加一遍就错了。

4 · 统一 scale producer 路径 ★ 本版新增 · +1.63%

观察。上一步留下四个 layout 函数。但因为 B_M == B_N == 256，于是 packed_sfa_tile_elem == packed_sfb_tile_elem == 256 × NUM_KGROUPS， 结果是 make_layout_gsfa_scale 和 make_layout_gsfb_scale 的函数体 逐字符完全相同，ssfa / ssfb 同理。

也就是说，wave 0 和 wave 1 走的是两条字面等价的代码路径，区别只在基地址和 stride。 编译器必须为两条分支各生成一套地址计算和布局常量，而它无法自己发现这两条能合并。

做法。把「两条分支」改写成「一条分支 + 提前选好的描述符」：

prologue —— 只算一次
const bool scale_producer_active = wave_id < 2;
const bool scale_producer_is_sfa = wave_id == 0;

const auto* g_sf_base = scale_producer_is_sfa
    ? ptr_sfa + batch_id*stride_sfa_batch + first_block_m*num_tiles_k*stride_sfa
    : ptr_sfb + batch_id*stride_sfb_batch + block_n    *num_tiles_k*stride_sfb;
auto g_sf = make_gmem(g_sf_base);

const int stride_sf = scale_producer_is_sfa ? kargs.stride_sfa : kargs.stride_sfb;

static_assert(T::packed_sfa_tile_elem == T::packed_sfb_tile_elem);
auto* s_sf_ptr = scale_producer_is_sfa ? s_sfa.ptr : s_sfb.ptr;

三个发射点（prologue、主循环、output tile 边界）从 if/else 双分支塌缩成单条：

改前
if (wave_id == 0) {
    async_load<16>(g_sfa, s_sfa.ptr, u_gsfa, u_ssfa + ssfa_offset(st), gsfa_offset(k));
} else if (wave_id == 1) {
    async_load<16>(g_sfb, s_sfb.ptr, u_gsfb, u_ssfb + ssfb_offset(st), gsfb_offset(k));
}
改后
if (scale_producer_active) {
    async_load<16>(g_sf, s_sf_ptr, u_gsfa, u_ssfa + ssfa_offset(st), gsf_offset(0, k));
}

注意改后只保留 u_gsfa / u_ssfa—— 因为 gsfb/ssfb 与它们逐字符相同，留一个就够，另一个连同它的布局常量一起消失。

前提被钉死 这个合并依赖 B_M == B_N。代码里那行 static_assert(packed_sfa_tile_elem == packed_sfb_tile_elem) 就是为此存在的： 将来若改成非方形 block tile，编译期直接报错，而不是安静地算错结果。

5 · 描述符跨 output tile 存活 ★ 本版新增

问题。上面那段被提到了 output_tile 循环之外。 但原版每进一个新的 M tile，都要为 SFA 重建一次 gmem 描述符：

改前 —— 每个 output tile 边界重算一次
auto g_sfa_next = make_gmem(
    ptr_sfa + batch_id*stride_sfa_batch + next_block_m*num_tiles_k*stride_sfa);

if (wave_id == 0) {
    async_load<16>(g_sfa_next, s_sfa.ptr, u_gsfa, ..., gsfa_offset(0));
} else if (wave_id == 1) {
    async_load<16>(g_sfb, s_sfb.ptr, u_gsfb, ..., gsfb_offset(0));
}

做法。把「前进到下一个 M tile」从重建描述符降级为偏移里加一项：

改后
// prologue，循环外
const int output_stride_sf = scale_producer_is_sfa ? num_tiles_k * stride_sfa : 0;

// 循环内
auto gsf_offset = [&](int output_delta, int tile_k) {
    return (output_tile + output_delta) * output_stride_sf + tile_k * stride_sf;
};

// 主循环用 delta=0（本 tile），output tile 边界用 delta=1（下一 tile）
async_load<16>(g_sf, s_sf_ptr, u_gsfa, u_ssfa + ssfa_offset(st), gsf_offset(1, 0));
这里有个巧妙处 output_stride_sf 对 SFB 恰好取 0。 这正是 fixed-B 语义在偏移算术里的自然表达——B 侧不随 M tile 前进。 于是同一个表达式同时正确覆盖了 SFA 的「每 tile 前进一格」和 SFB 的「原地不动」， 不需要任何分支。

6 · B-first：最冷的请求最早发射 调度

问题。B 的跨 block cache 复用最弱，最容易成为一个 tile 里最后完成的 global-to-LDS 请求，从而卡住 barrier。

做法。把最冷的请求排到最前面开始"老化"，让易命中 cache 的 scale/A 去覆盖 LDS 延迟：

B0 → B1 → 当前 tile 的早期 LDS reads → scale → A0 → A1

在代码里体现为主循环的发射次序：先 load_b_range_scale，再 load_next_scale()，最后两条 A：

v_b = load<VEC_B>(s_b, u_rb + sb_offset(stage, 0));
load_b_range_scale<T, 0, b_ds_read_insts/2>(s_b, rb1_offsets_prefetch, v_b_second);
__builtin_amdgcn_sched_barrier(0);

load_next_scale();                                       // ← scale 在 B 之后
async_load<VEC_A>(g_a, ..., ga_offset(0, tile + 1), 0_I, number<0>{});
async_load<VEC_A>(g_a, ..., ga_offset(1, tile + 1), 0_I, number<0>{});

ATT 观测到的效果：

指标改前改后
两个 head lgkmcnt(5)82.94.0 cyc/tile
barrier residence335.6258.1 cyc/tile
tile-tail VMEM wait196.8207.9 cyc/tile

尾部 VMEM 等待略有变差，但 head wait 降得更多，净为正。

7 · asymmetric B producer 调度

问题。B0/B1 若由 resident pair 的两个 wave 各搬一半，两条 wave 会互相等。

做法。resident pair 是 (0,4) (1,5) (2,6) (3,7)。 在 mid-tile barrier 之后，只让 pair 里的一条 wave 搬完整个 B， 另一条立刻进入尾部 12 条 MFMA： 

if (tile + 2 < loops) {
    constexpr int b_producer_wave_n = 1;        // 每个 pair 里 n==1 的那条搬 B
    if (wave_id_n == b_producer_wave_n) {
        async_load<VEC_B>(g_b, s_b.ptr, u_gb_producer_0, ..., gb_offset(0, tile+2));
        async_load<VEC_B>(g_b, s_b.ptr, u_gb_producer_1, ..., gb_offset(0, tile+2));
        async_load<VEC_B>(g_b, s_b.ptr, u_gb_producer_0, ..., gb_offset(1, tile+2));
        async_load<VEC_B>(g_b, s_b.ptr, u_gb_producer_1, ..., gb_offset(1, tile+2));
    }
    __builtin_amdgcn_sched_barrier(0);
}
__builtin_amdgcn_s_setprio(1);
// ↓ 两条 wave 都继续跑完全相同的 12 条 MFMA

producer wave 用两个显式的 logical wave-N layout （u_gb_producer_0 / u_gb_producer_1）代替自己那份， 从而覆盖本该由伙伴负责的那一半。

关键区别 这不是严格的 producer/consumer 分离（那个方向实测 NO-GO）。 producer wave 只是短暂落后，并没有放弃计算——两条 wave 仍执行全部 MFMA。 代价是几条 VMEM 的延迟，收益是伙伴 wave 提前 12 条 MFMA 开跑。

8 · B1 半程读取：拆成 prefetch + tail 两段 调度

问题。B half 1 的那组 ds_read 如果一次读完， 后面 32 条 MFMA 全都得等它；如果一条不读，用到时又要现等。

做法。对半劈开。前一半在 tile 开头就发，后一半推迟到真要用 v_b_second 之前：

// tile 开头：先发一半
auto rb1_offsets_prefetch = layout_to_offsets<VEC_B>(u_rb + sb_offset(stage, 1));
load_b_range_scale<T, 0, T::b_ds_read_insts / 2>(s_b, rb1_offsets_prefetch, v_b_second);

// ... 中间 32 条 MFMA 只用 v_b（half 0），与上面的读重叠 ...

// 真正要用 half 1 之前：补上后一半
auto rb1_offsets_tail = layout_to_offsets<VEC_B>(u_rb + sb_offset(stage, 1));
load_b_range_scale<T, T::b_ds_read_insts / 2, T::b_ds_read_insts>(
    s_b, rb1_offsets_tail, v_b_second);
const auto& v_b_n1 = v_b_second;

提前条数扫描过 2/4/6/8：r4 与 r8 性能只差 0.008%，但 r8 多花 15 个 VGPR， 所以取 r4。ATT 里 B1 progressive wait 从约 41 降到 0.8 cyc/tile。

9 · ds_read2st64_b32：SFB 两 half 一条读完 scale 通路

观察。SFB 的 half 0 与 half 1 在 LDS 里恰好相距 512 字节。 而 ds_read2st64_b32 的 offset 单位是 64 dword = 256 字节。 512 / 256 = 2，所以 offset1:2 正好命中——两条读能合成一条： 

auto load_sfb_pair = [&](int read_stage) {
    const auto offsets = layout_to_offsets<4>(u_rsfb_0 + ssfb_offset(read_stage));
    const u32_t addr = static_cast<u32_t>(
        reinterpret_cast<__UINTPTR_TYPE__>(s_sfb.ptr + offsets[0]));
    u32x2_t pair;
    // SFB half 1 is exactly 512 bytes after half 0. ST64 offsets are in
    // units of 64 dwords (256 bytes), hence offset1=2.
    asm volatile(
        "ds_read2st64_b32 %0, %1 offset0:0 offset1:2\n"
        : "=v"(pair) : "v"(addr) : "memory");
    return pair;
};

展开后静态 ds_read 从 162 降到 156，VGPR 少 4 个。 绝对收益很小（中位 +0.04%、均值 +0.12%），5/5 组方向一致， 作为组成部分保留，不单独宣称提速。

这里用内联汇编而不是 intrinsic，是因为需要精确控制 offset0/offset1 这对立即数； 注释把「512 字节 ÷ 256 字节 = 2」这个推导写进了代码，防止后人改 LDS 布局时踩雷。

10 · 累加器 pin：阻止编译器搬运 C 寄存器

问题。C 累加器是 2×2 组、每组 16 个 fp32， 占了 VGPR 预算的绝大部分。编译器在寄存器压力下很容易决定「把这块 C 挪个位置」， 插入一堆 v_mov_b32，甚至溢出。

做法。每条 MFMA 之后，用一个空的内联汇编把累加器"钉"在原地：

mma_scale_repeat_n2<T, 0, 0, 0>(mma, v_a[0], v_b, v_c[0][0], v_sfa, v_sfb[0]);
{
    auto* v_c_pin = reinterpret_cast<vector_t<D_ACC, 16>*>(&v_c[0][0]);
    asm volatile("" : "+v"(v_c_pin[0]) ::);      // 空指令，但 "+v" 声明读写该寄存器组
}

asm volatile("") 不产生任何机器码，但 "+v" 约束告诉编译器 「这组 VGPR 在这里被读写了」，于是它不能跨这个点搬动或重分配它们。 整个主循环里这个模式重复 16 次（每条 MFMA 后一次）， 分别钉 v_c_pin[0] 和 v_c_pin[1]（每组 C 的上下半）。

结果就是最终 ISA 里 vspill = 0、scratch_* = 0， 在 240/256 VGPR 这么紧的预算下没有任何溢出。

11 · sched_group_barrier：手工指定交错比 调度

问题。编译器自己排 MFMA 和 LDS 读的交错比例，排出来的不一定是最优。

做法。用 sched_group_barrier 显式指定一个重复的配比模式：

__device__ inline void sched_barrier_pairs_scale() {
    __builtin_amdgcn_sched_group_barrier(0x08, 1, 0);   // MFMA   × 1
    __builtin_amdgcn_sched_group_barrier(0x02, 2, 0);   // VALU   × 2
    __builtin_amdgcn_sched_group_barrier(0x08, 1, 0);   // MFMA   × 1
    __builtin_amdgcn_sched_group_barrier(0x02, 2, 0);   // VALU   × 2
}

掩码 0x08 是 MFMA、0x02 是 VALU。这段在每条 mma_scale_repeat_n2 之后调用一次，把「1 条 MFMA 配 2 条 VALU」 这个节奏铺满整个 MFMA 段——让地址计算和 scale 解包的 VALU 指令 均匀塞进 MFMA 的执行间隙，而不是堆在一起。

另外在关键的发射边界上用 __builtin_amdgcn_sched_barrier(0)（完全禁止跨越移动）， 把「B 读 → scale → A」这个顺序焊死，防止编译器把第 6 步辛苦排好的顺序又打乱。

12 · s_setprio：MFMA 段抬优先级 调度

问题。两条 resident wave 共享一个 SIMD。搬运阶段的 wave 会和 正在算 MFMA 的 wave 抢发射槽。

做法。进 MFMA 段抬优先级，出来降回去：

s_waitcnt_lgkmcnt(number<8>{});
__builtin_amdgcn_s_setprio(1);        // ← 进入 MFMA 段
    ... 32 条 MFMA ...
__builtin_amdgcn_s_setprio(0);        // ← 出来，让搬运 wave 上
    s_waitcnt_vmcnt(0); s_waitcnt_lgkmcnt(0); s_barrier();
    发 t+2 的 cold B
__builtin_amdgcn_s_setprio(1);        // ← 再抬，跑尾部 12 条 MFMA
    ... 32 条 MFMA ...
__builtin_amdgcn_s_setprio(0);

效果是让 MFMA 段尽量不被打断，同时把 barrier 附近那段 （本来就要等的地方）让给需要发 VMEM 的 wave。

13 · 单 barrier 同时发布与回收 同步

问题。双缓冲天然需要两件事：发布 tile t+1 的数据（写完了，可以读）， 回收 tile t 的 LDS stage（读完了，可以覆盖）。两个 barrier 是最直观的写法， 但 barrier 本身很贵。

做法。把两件事合并到同一个 barrier 上，放在整个 tile 的正中间：

// tile t 的全部操作数此刻已经在 VGPR 里了
__builtin_amdgcn_s_setprio(0);
s_waitcnt_vmcnt(0_I);          // t+1 的 global→LDS 全部落地
s_waitcnt_lgkmcnt(0_I);        // t 的 LDS 读全部完成
__builtin_amdgcn_s_barrier();  // ← 一个 barrier 同时完成发布与回收
__builtin_amdgcn_sched_barrier(0);

这能成立的前提是那句注释点明的： 「tile t 的全部操作数此刻已经驻留在 VGPR 里」—— 所以回收它的 LDS 是安全的。barrier 之后立刻发 t+2 的 cold B， 让这条最冷的请求在尾部 12 条 MFMA 的掩护下开始老化。

测过更激进的方向：把 barrier 删掉（nobarrier）反而 −2.4%—— barrier 保护的调度顺序本身有价值，不只是正确性开销。

14 · 尾 tile 剥离 结构

问题。主循环条件是 tile + 1 < loops， 最后一个 K tile 被故意留在循环外。 如果放进循环，每轮都要判断「还要不要发下一个 tile 的 global load」。

做法。循环只处理「有下一个 tile」的情形；最后一个 tile 单独展开，只消费不发射：

// Consume the final resident tile without issuing more global loads.
v_sfa = bit_cast<D_SF_PACK>(load<4>(s_sfa, u_rsfa + ssfa_offset(scale_stage)));
const auto v_sfb_pair = load_sfb_pair(scale_stage);
v_a[0] = load<VEC_A>(s_a, u_ra + sa_offset(stage, 0));
v_a[1] = load<VEC_A>(s_a, u_ra + sa_offset(stage, 1));
v_b    = load<VEC_B>(s_b, u_rb + sb_offset(stage, 0));
s_waitcnt_lgkmcnt(0_I);

这段腾出来的发射带宽，正好用来预取下一个 output tile 的 K=0 数据—— 于是 M tile 之间的切换不需要冷启动： 

const bool has_next_output =
    output_tile + 1 < T::OUTPUT_TILES_PER_WG && block_m + 1 < num_tiles_m;

if (has_next_output) {
    auto g_a_next = make_gmem(ptr_a + batch_id*stride_a_batch + next_row*stride_a);
    if (scale_producer_active) {
        async_load<16>(g_sf, s_sf_ptr, u_gsfa,
                       u_ssfa + ssfa_offset(next_output_stage), gsf_offset(1, 0));
    }
    async_load<VEC_A>(g_a_next, ...);   // A 换新行
    async_load<VEC_B>(g_b, ...);        // B 复用同一个描述符（fixed-B）
    ...
}
// ↓ 这些搬运与尾 tile 的 64 条 MFMA 重叠

注意这里 g_b 直接复用——这就是第 1 步 fixed-B 的兑现点： 换 M tile 时 B 侧一个字节都不用重读。而 scale 侧靠第 5 步的 gsf_offset(1, 0) 一个表达式搞定（SFA 前进一格、SFB 因 output_stride_sf == 0 原地不动）。

15 · C 写回 non-temporal 访存

做法。C 写完就不会再读，不该污染 L2。给四次 store 都加上 nt 提示 （第三个模板参数 number<2>{}）： 

store<VEC_C>(g_c, v_c[0][0], u_gc, c_offset(0, 0), number<2>{});
store<VEC_C>(g_c, v_c[0][1], u_gc, c_offset(0, 1), number<2>{});
store<VEC_C>(g_c, v_c[1][0], u_gc, c_offset(1, 0), number<2>{});
store<VEC_C>(g_c, v_c[1][1], u_gc, c_offset(1, 1), number<2>{});

16 · #pragma unroll 4 与它的门禁 代码生成

主 K 循环上就一行 pragma，但它是这个内核里单步收益最大的一处： 

#pragma unroll 4
for (tile = 0; tile + 1 < loops; ++tile) {

问题是 clang 20/21/22 会直接忽略它（报 loop not unrolled）， 循环体保持 64 条 MFMA。只有 clang 23 会真的展开 3 倍：

编译器MFMA汇编行分支ds_read
clang 20（未展开）6413542552
clang 23（展开）192258749156

本机上这个差异值 16%。真正的自变量是「展开与否」而不是编译器版本—— 在另一台机器上，clang 22 编手动展开版和 clang 23 编自动展开版，性能完全相同。 clang 23 的价值是省掉维护一份手动展开源码的负担。

门禁 因为「展开被静默关掉」会安静地损失 16%，构建里挂了一道硬门禁—— 它从链接后的 exe 里抽 device image 数 MFMA 条数，少于 192 直接失败： 
n=$(llvm-objdump -d $DEV | grep -c v_mfma_scale_f32_16x16x128)
if [ "$n" -ge 192 ]; then echo "OK -- $n MFMA (loop unrolled)";
else echo "FAIL -- only $n MFMA"; exit 1; fi

必须从链接后的 exe 抽，不能看内核 TU 的 .s—— hipcc 自己的 device image 会静默覆盖 -fembed-offload-object， 这个坑制造过一次「clang 23 无收益」的假结论。

5. 这个内核已经用尽的空间

VGPR 墙 当前 240 / 256，occupancy 2 waves/SIMD。每 wave 26 条 LDS 读配 32 条 MFMA 已经在算法下界，想再往上只能加大 wave tile 来摊薄每条读， 而更大的 wave tile 需要更多累加器 VGPR——没有空间。

消融实验（用故意不正确的 diag 内核定价）给出的上界说明缺口在数据通路，不在指令排布：

消融性能增量含义
保留版2.828 P—基线
放开全部 lgkmcnt + vmcnt2.857 P+1.0%等待全删也只值 1%
去掉全部 global load3.373 P+18.0%数据通路的真实开销
再去掉 C store3.747 P+11.1%skeleton 允许 3 P

最后一行有个教训：那 11.1% 是在 global load 流已被移除的前提下量的。 据此判定「是延迟、可靠重排回收」并实现之后，只拿到 +0.17%—— 真实原因是读写争用。消融数字只在它自己的消融上下文里有效。

unified scale 省的 3 个 VGPR 不足以撼动那堵墙。但它证明了一件事： 「两条字面等价的代码路径」这类冗余在这个内核里仍然存在，单条就值 1.6%。
